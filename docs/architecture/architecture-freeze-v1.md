## 4. Service boundary review — decisions

Every direct Supabase call reachable from React was classified per ADR-0001.

| Location                                  | Call                          | Category | Decision |
| ----------------------------------------- | ----------------------------- | -------- | -------- |
| `routes/auth.tsx`                         | `auth.getSession`, `onAuthStateChange` | A | Keep — auth infrastructure |
| `routes/__root.tsx`                       | `auth.onAuthStateChange`      | A | Keep |
| `routes/_authenticated/route.tsx`         | `auth.getUser` + gate reads   | A | Keep — route gate must run before any service |
| `routes/_authenticated/perfil.tsx`        | `auth.signOut`                | A | Keep |

**No component was refactored**, because no Category C violation was found and
wrapping Category A calls would have been artificial abstraction — explicitly
forbidden by this sprint's rules.

## 5. Service API consistency review

Reviewed: `WorkoutGeneratorService`, `TrainingPlanService`, `XPService`,
`AchievementService`, `ProgressionService`, `GamificationOrchestrator`.

Findings:

- Async conventions, `userId` resolution, and result-object shapes are already
  consistent across all six.
- Error behaviour is consistent: engines throw, the Orchestrator collects
  stage failures into `result.errors` and returns a partial result.
- One duplicated alias (`regenerateTrainingPlan` / `regenerateProgram`) —
  **retained** for backward compatibility, marked `@deprecated`.
- "Plan" vs "Program" vocabulary is mixed in method names. Renaming would be a
  breaking change with no correctness benefit, so it was **not** performed. The
  distinction (plan = structure, program = the user's active run of a plan) is
  now documented in `training.md`.

**No API was renamed and no breaking change was introduced.**

## 7. Database findings and changes

One migration was applied — every statement fixes a concrete audit finding.

**Fixed:**

1. **Four exact duplicate indexes dropped** — `idx_training_weeks_plan`,
   `idx_training_days_plan`, `training_days_plan_week_day_idx`,
   `idx_planned_workouts_plan`. Each duplicated an existing unique index on
   identical columns and only cost write throughput.
2. **Eleven missing foreign keys added** on `user_id` →
   `auth.users(id) ON DELETE CASCADE` for `training_plans`, `training_weeks`,
   `training_days`, `planned_workouts`, `generated_workouts`, `user_stats`,
   `user_progression`, `xp_history`, `level_history`, `user_achievements`,
   `user_achievement_progress`. Deleting an account previously orphaned
   training and gamification data. Verified **zero** orphan rows before
   applying, so no data was touched.
3. **RLS role scoping normalised** — `training_weeks`, `training_days` and
   `planned_workouts` policies were implicitly `PUBLIC`; they are now
   `TO authenticated`, matching every other table. Effective access is
   unchanged (`auth.uid()` is `NULL` for anon). **No policy was weakened.**

**Verified healthy:** RLS enabled on every user table, idempotency unique
constraints in place, Data API grants present, database linter reports zero
issues.

**Not changed:** no table, column or type was added, removed or renamed.

## 11. Technical debt intentionally retained

Each item was evaluated and deliberately **not** addressed, because fixing it
would have required product-behaviour change, redesign or speculative
refactoring — all forbidden by this sprint.

| # | Debt | Why retained |
| - | ---- | ------------ |
| 1 | **Client-authoritative gamification.** XP and level writes originate in the browser; RLS protects ownership, not rules. | Moving writes behind `createServerFn` is a trust-boundary redesign, not a stabilisation. **Highest-priority Phase 7 item.** |
| 2 | **Dual XP storage** (`user_stats` and `user_progression` both hold XP). | Unifying them changes persistence semantics for a live gamification system. Both are written in the same pipeline, so drift is currently contained. |
| 3 | **`TrainingPlanService` is ~700 LOC** and mixes orchestration with data access. | A repository split is a stylistic refactor of working, tested code. |
| 4 | **Mixed fetching paradigms** — training uses TanStack Query, gamification hand-rolls `useEffect` + event bus. | Both work correctly; converging them is a paradigm change, not a bug fix. |
| 5 | **`GamificationResult` is overloaded** — it serves both "what just happened" and "current snapshot". | Splitting the type touches every consumer. |
| 6 | **No route-level code splitting**; i18n bundles load eagerly. | Performance optimisation, out of scope for a freeze. |
| 7 | **Magic strings for statuses** instead of const unions. | Cosmetic; no correctness impact. |
| 8 | **Test coverage gaps** on plan generation and workout completion. | New tests are welcome additions but not required to freeze; the execution path is now standardised. |
| 9 | **Large route components** (some 900+ LOC). | Splitting risks UI regressions for no architectural gain. |
| 10 | **13 Fast-Refresh lint warnings.** | Development-only ergonomics. |

## 12. Known limitations

- Gamification rules are enforceable only client-side (see debt #1).
- Event buses are in-process and do not survive a reload; persisted state is
  the source of truth.
- The app is a PWA, not a native build; notifications depend on browser or
  Capacitor support.

## 13. Rules for future phases

The binding guardrails live in
[`conventions.md`](./conventions.md) — RULE 1 through RULE 8. In short:

1. Components own no domain logic.
2. `TrainingPlanService` owns the training runtime.
3. `XPService` owns XP.
4. `ProgressionService` owns levels.
5. `AchievementService` owns achievements.
6. The Orchestrator coordinates and duplicates nothing.
7. Domains integrate via public APIs and events, never via foreign tables.
8. No new abstraction without a real use case.

### Future Application Runtime (direction only — do not implement)

A future *Application Runtime* could host domains uniformly — Training,
Gamification, Goals, Nutrition, Notifications, AI Coach — each registered
through the existing plugin port
(`GamificationOrchestrator.registerEngine`) or an equivalent. This is recorded
as a **possible direction only**. No speculative code exists or should be
written for it. YAGNI applies.
